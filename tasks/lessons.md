## Carried forward from HANDOFF.md (pre-2026-07)

- **[pre-2026-07]** | Flask `debug=True` auto-reloader can execute half-saved migration code against live `catalog.db`, corrupting rows | Write `s2d/db.py` migrations correct in ONE edit; if forced to iterate, immediately verify + repair data via a direct sqlite3 check.
- **[pre-2026-07]** | Browser-automation `form_input` on a checkbox sets the DOM `.checked` without firing React `onChange`, so state stays stale | For controlled checkboxes, dispatch a native `click()` via `javascript_tool`; never use `form_input`.
- **[pre-2026-07]** | Two schema-fetching `useEffect`s in `TestCasePanel.jsx` had a race: switching mappings quickly let a stale fetch resolve after a newer one and overwrite state with the wrong mapping's schema | For any effect that fetches per-selection data, use a `cancelled` flag + cleanup function.
- **[pre-2026-07]** | Destructive drop-and-recreate migrations (`_migrate_stale_schema_if_needed` pattern) risk data loss and were rejected by the user | Schema migrations must be additive: `ALTER TABLE ADD COLUMN` + backfill from old columns. Never drop-and-recreate for a shape change.

## 2026-08-05

- **[2026-08-05]** | A cross-page "focus" handoff (App.jsx `s2dFocus` → S2DPage → TestCasePanel, used by Test Suites' "Edit Suite"/"Edit test case" buttons) worked in isolated logic review but silently failed in the browser: the effect that consumed `focus` also called a callback to clear it in the parent immediately after acting. Under React 18 StrictMode's dev-only double-mount check (mount → cleanup → remount, to verify effects are safely re-runnable), the first throwaway mount's effect cleared the parent's trigger before the second real mount could see it — so the real mount had nothing left to act on. | Any state meant to survive a component being torn down and rebuilt (cross-page handoffs, one-shot "do X then reset" triggers) must NOT be cleared by the same effect that consumes it. Clear it only on an unambiguous, unrelated user action (here: `goToPage`, i.e. any manual sidebar nav) so a StrictMode remount of the subtree sees the identical trigger value both times and produces the identical result — true idempotency, not just "runs without crashing twice."
- **[2026-08-05]** | Added a `useEffect` that referenced `startEdit`/`enterSuiteSelection`/`loadSuiteMembers` (consts defined later in the same component) before their declaration lines. It's actually safe at runtime — the effect callback only executes after the full render function has finished, by which point all consts are assigned — but ESLint's `no-use-before-define` check is purely static and doesn't know that, so it correctly flagged it as a real lint error, not a false positive. | When an effect needs to call handlers defined later in a large component, physically move the effect below those handlers' declarations rather than reaching for a suppression comment — the static-ordering rule is enforcing a real readability property even when the runtime behavior is safe.

## 2026-08-06

- **[2026-08-06]** | While setting up a fixture to verify cascade-delete, grabbed `mappings[0]` from the live API to attach a throwaway test suite + schedule to — turned out to be "D to source," the user's real, current, in-progress mapping (built around freshly-uploaded Kaggle data), not leftover test data. Caught it by checking the mapping list again before running the actual destructive delete, and cleaned up the attached suite/schedule without touching the mapping itself. | Before attaching anything to "the first mapping/connector/whatever the API returns" for test-fixture purposes, print the full list and read the names — never assume index 0 is disposable, especially in a session where the user has been actively doing real work between turns. For genuinely destructive verification (deleting a mapping to prove cascade behavior), always build a dedicated, obviously-named throwaway object first rather than repurposing anything that already exists.

## 2026-08-12 to 2026-08-14

### Platform constraints — verified, don't re-derive these

- **[2026-08-13]** | Tried to count every table in a container with ONE query: `SELECT '<name>' AS table_name, COUNT(*) FROM <t>` UNION ALL'd per table. Against a live Fabric Lakehouse it returned **silently wrong numbers** — for four tables whose true counts were `[97377, 0, 1000, 883]` it gave `[97377, 0, 0, 97377]`, arms 3 and 4 repeating arms 1 and 2. Two arms were fine, four were not; it happens with or without the string literal, and several scalar subqueries in one SELECT are corrupted the same way. Caught only because a table showed `0 rows` in the UI that a direct `COUNT(*)` said had 1000. | **DuckDB's mssql extension mis-pushes MULTIPLE AGGREGATES in one statement.** Never combine per-table aggregates into a single query against Fabric — issue one `COUNT(*)` per table on the already-open connection (the connection is the expensive part at ~9s; each query is <1s). **Row-level multi-arm unions are unaffected** — `COUNT(*)` over a 4-arm `SELECT 1 FROM t` union was exactly right — which is why `s2d/engine.py`'s `_build_column_union` is safe. The warning lives in `build_row_count_query`'s docstring because "combine these into one query" is the obvious optimisation someone will try again.
- **[2026-08-14]** | Fabric exposes **no per-activity pipeline detail**: `queryactivityruns` and `activityruns` both 404, and a job instance carries only status/times/`failureReason`. `getDefinition` does work, but decoding all five real pipelines showed it would be blind for three (ForEach driven by a config table, a bare notebook, an `InvokeCopyJob`). | To report what a pipeline did, **measure the effect** (row counts before/after) rather than reading its declared config. Don't spend time re-investigating the activity APIs.
- **[2026-08-13]** | Two Lakehouses in one workspace share a SQL endpoint server, but `_duckdb_attach` attaches only one as `fabric_db`, so a three-part name to the other fails with `Catalog "..." does not exist`. | Cross-Lakehouse joins in a single statement are **not** available as the connector is written. `shares_connection()` (connector AND container) is the correct gate for "one script can reach both sides". Attaching both catalogs would probably work but is unproven.
- **[2026-08-13]** | The `SQL_PLACEHOLDER` shown in the Custom SQL editor used `CAST(...) + ' text'` — T-SQL string concat, which **fails in DuckDB**. The example testers are most likely to copy didn't run. | Everything is parsed by DuckDB (Local directly, Fabric via the mssql extension). `TOP`, `GETDATE()`, `ISNULL()` and `+` on strings all fail; use `LIMIT` and `||`. Check example/placeholder SQL actually executes, not just that it reads plausibly.

### Testing against a live, actively-changing workspace

- **[2026-08-13]** | A verification "failed" because a Fabric table read 500 rows in one call and 1000 in the next — the user was running pipelines between my two calls. I nearly recorded a nonexistent bug. Later the *inverse* happened: I dismissed a genuine wrong-count as "data changed" when it was a real bug. | When comparing a computed value against a "truth" query on a live system, **take both readings in the same moment**, and treat a disagreement as a bug only when two back-to-back truth reads agree with each other and disagree with the value. Otherwise the data moving underneath is indistinguishable from a defect — in both directions.
- **[2026-08-14]** | Several of my own verification scripts were wrong, not the code: expected 3 poll ticks after waiting for 2; asserted `'banana' AS passed` should ERROR when it has always meant FAIL; patched `run_query_all` after the code moved to `run_query`; and simulated a scheduler "restart" by calling `init_scheduler()` twice — which early-returns when already started, so it proved nothing. | When a test fails, **check the test before the code**. And when simulating a lifecycle event (restart, remount, reconnect), verify the simulation actually reproduces it — here that meant tearing `_scheduler` down to None first.
- **[2026-08-13]** | Browser assertions kept failing on text that was visibly present: CSS `text-transform: uppercase` makes `innerText` return `RECENT RUNS`, not `Recent runs`. | Match browser text **case-insensitively**, or read `textContent` — never assume `innerText` matches the source string.

### Traps in this codebase

- **[2026-08-13]** | Rendering a row count with `count || '—'` hides `0`, because `0` is falsy — suppressing exactly the case worth noticing, since a rule over an empty table passes trivially and proves nothing. | Use `??` not `||` for any numeric that can legitimately be zero, and test the zero case explicitly with a real empty table.
- **[2026-08-14]** | `bump_schedule_misfire` was `table = 's2d_suite_schedules' if kind == 'suite' else 'harvest_schedules'`. Adding a third schedule kind would have silently UPDATEd the **wrong table** — no exception, no log. Two more spots fail just as quietly: `_on_job_missed`'s hardcoded kind tuple, and `init_scheduler`'s re-registration loops (miss one and those schedules survive in the DB, still read as active, and never fire again after a restart). | There is **no central registry of schedule kinds**. `s2d_db.SCHEDULE_TABLES` is now the one dispatch dict and raises on an unknown kind; the listener keys off it. Any new kind still needs its own `init_scheduler` loop, routes, api.js block and dashboard table — grep for an existing kind name before assuming you're done.
- **[2026-08-13]** | `validate_select_only` required the script to *start* with `SELECT`, but two shipped templates (`referential_check`, `custom_expression`) open with a `--` comment, so any test case built from them failed at run time. A comment mentioning "delete" also tripped the forbidden-keyword search. | Guards that inspect SQL text must strip comments (quote-aware — `'a--b'` is data) before checking. Fixed in `_strip_sql_comments`.
- **[2026-08-14]** | `_run_sql_check` surfaced only a column literally named `details`, so a script computing `COUNT(*) AS male_count` reported a bare PASS and threw the number away. | A test script's other columns are the tester's own output — show them. Related: contract columns (`passed`, `value`) are now optional, but a script that *declares* `passed` must never be silently reclassified as a measurement.

## 2026-08-16

- **[2026-08-16]** | Asked to make SQL tests run against JSON/XML/TXT, the tempting shape is to teach the query layer about formats. The codebase already made that unnecessary: `LocalConnector` exposes every upload as a real DuckDB table, so widening ONE function (`ingest_file`) gave the pickers, row counts, syntax checker, all 10 templates, the 8 parity metrics, suites and schedules the new formats for free. | **Normalise at the edge, not in the query layer.** Before building a feature that spans the stack, check what the existing abstraction already carries — here the entire ask reduced to a reader dispatch plus a flatten step, and *no* engine or connector change. Verify the claim directly: the same records as six formats, one identical SQL, identical results **and** identical schemas.
- **[2026-08-16]** | The XML→rows heuristic ("most frequent child of the root") produced three wrong shapes: `<root></root>` became 1 empty row instead of 0; a genuine single record turned each of its *fields* into a row; and a collection containing exactly one `<item>` produced different column names than the same file with two items. | Row-shape heuristics need the degenerate cases decided explicitly: **empty → 0 rows** (the count a tester most needs to notice), several unique children → one record, exactly one child → still a collection. The last one matters most: **column names must not change with the number of records**, or a test written against a one-row file breaks against a two-row one.
- **[2026-08-16]** | A "malformed file" test appeared to expose a bug — after a deliberate failure, the next operation died with `TransactionContext Error: current transaction is aborted`. It was the *test* reusing one DuckDB connection across failures; `ingest_file` opens and closes one per call, so production can't reach that state. | Reinforces the existing rule: **check the test before the code.** Specifically, when a test drives failures in a loop, confirm it recreates the per-call resource lifecycle the real code uses, or it invents faults that can't happen.
- **[2026-08-16]** | A scripted multi-file edit silently matched nothing: `TestCasePanel.jsx` is **CRLF** while most of the repo is LF, so `\n` markers never matched. Reading with universal newlines and writing back would have rewritten every line, burying a 10-line change in a whole-file diff. | Line endings are **per file** here, not per repo. Any scripted edit must read with `newline=''`, detect the file's own ending, build markers from it, and write with `newline=''`. Check the diff line count afterwards — a small change showing as a full-file rewrite means the endings were flipped.
- **[2026-08-16]** | Source-only validations needed the `destination_*` columns to be absent, but they're `NOT NULL` and SQLite can't drop a constraint without rebuilding the table — exactly the destructive migration that's already been rejected once. | When additive-only migration collides with an existing `NOT NULL`, **store an empty value rather than rebuilding the table**, and make every read path treat empty as absent. A new `validation_kind` column with a DEFAULT then needs no backfill at all: existing rows are already correct.
